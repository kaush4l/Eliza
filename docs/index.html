Connecting your LLM (any OpenAI-compatible endpoint)

Nothing about the model is baked into the image. Hermes needs one thing: an OpenAI-compatible endpoint that supports tool calling. Local servers (omlx, LM Studio, Ollama, llama.cpp, vLLM, TGI) and hosted APIs (OpenAI, OpenRouter, Together, Groq, Fireworks, your own gateway) all work.

  1. Paste the base URL — it should end in /v1. Add an API key if the endpoint needs one; it is sent only to that endpoint and stored in this browser.
  2. Press Connect: the page lists the endpoint's models, fills the field, and picks up the advertised context window when there is one.
  3. Local servers need CORS. LM Studio: Developer → Enable CORS. Ollama: OLLAMA_ORIGINS=*. llama.cpp/vLLM: allow this origin.
  4. Changing endpoint, model or key after the VM has started needs a reload — the values are handed to the guest at boot. Inside the TUI you can also switch with hermes' own /model command.

On the hosted (https) page, Chrome gates local-network requests. Loopback is exempt from mixed-content rules, but Local Network Access is a separate permission: the first call to 127.0.0.1 is blocked (net::ERR_FAILED, the agent then sits waiting) until you allow it — address-bar icon → Site settings → Local network access → Allow, then reload. Two alternatives that need no permission: serve this same docs/ directory yourself (python3 serve.py 8917, then open http://127.0.0.1:8917/), or point the LLM field at a remote OpenAI-compatible endpoint over https.

State: ~/.hermes (sessions, memories, skills) and ~/work are sealed with AES-256 under a browser-local passphrase and stored in this browser (Cache API), then restored on the next boot. Nothing leaves your machine. Saving is on demand: click Save state.

URL overrides: ?backend=<url> · ?model=<name> · ?key=<api key> · ?guest=shell boot to a shell instead of hermes · ?persist=0 amnesia boot · ?image=<url> load an unchunked .wasm.

Speed and the dashboard — what is possible in here

Where a turn's time goes. Measured on this build: the model answers in the time it always would (the page talks to it directly — first byte in tens of milliseconds), and the rest is the Bochs interpreter running CPython. A turn is roughly ~10s of real guest CPU plus the model, and the first turn after boot used to add ~40s of lazy Python imports, since emulated disk reads run at about 1.5 MB/s. Those imports are now warmed during boot, hermes' auto-title second model call is off, and the idle TUI repaint is disabled.

Why hermes' own web dashboard is not exposed. The VM reaches the network only by handing HTTP requests to this page (the c2w proxy is outbound-only); nothing can dial into the guest, so a uvicorn server inside it is unreachable — and tunnelling every dashboard asset back through a poll channel would be slower than the terminal it replaces. The panel on the right is the page-side equivalent: endpoint, model, live context use, agent state and every relayed API call with timings, all rendered at native speed and costing the guest nothing. If you want the real dashboard, run c2w-net locally and boot with ?net=delegate=ws://…, which gives the guest actual TCP.
